# 04. Agent 契约 — 课程生成的规则

> 这份文件定义 Agent 生成课程时的硬约束。它直接喂给 prompt，也是 Backend 的校验依据。

---

## 一、Agent 的角色

Agent 不是写手，不是百科搬运工。它是**叙事生成助手**：

- 先通过 AI 澄清对话理解真实学习需求
- 负责将课程计划展开为连续的散文叙事
- 产出必须通过引擎校验 + LLM 评审 + 人工审核
- 生成的内容是教学叙事，不是教材摘要

---

## 二、澄清契约

生成前必须先产出 `contract`。这个 contract 必须来自 AI 参与的多轮澄清，不允许用固定问卷模板代替。

澄清助手的任务不是收集表单字段，而是识别用户真正卡住的地方：

- 用户观察到的具体差异现象是什么
- 这个差异属于落差、模型失配，还是系统悖论
- 用户说出的目标是不是只是指标，背后的系统理想状态是什么
- 用户当前缺少什么对象、关系、条件或边界模型
- 用户已有背景是什么
- 这个困惑为什么重要
- 课程应该讲什么、不讲什么、讲到什么深度

澄清标准：好的 `drivingQuestion` 必须面向差异性现象。它不能只是“如何学好 X”“X 是什么”“如何理解 X”，而要逼出比较关系：同一对象在不同条件下为什么表现不同、直觉与观察哪里冲突、为什么某个解决动作反而维持问题。用比较和差异倒逼细节和关系。

问题框定分三类：

- `gap`：现状与目标状态之间的落差。重点是区分指标和真正的系统目标。
- `model_mismatch`：旧模型解释不了观察到的现象。重点是找到缺失的对象、关系、条件或边界。
- `system_paradox`：解决问题的动作反而制造或维持问题。重点是识别第一序改变失效，需要第二序改变。

澄清完成后输出：

```json
{
  "drivingQuestion": "贯穿全课的具体问题",
  "centralTension": "直觉与真实结构之间的矛盾",
  "knowledgeType": "conceptual | procedural | factual | strategic | metacognitive | situational",
  "audience": "明确受众",
  "desiredOutcome": "学完后可检验的解释/判断/行动能力",
  "scope": {
    "include": ["必须讲的核心对象"],
    "exclude": ["明确不讲的内容"],
    "depth": "深度取舍"
  },
  "problemFraming": {
    "phenomenon": "用户观察到的具体现象",
    "contrast": "A/B 差异、条件变化或直觉与现实的冲突",
    "problemNature": "gap | model_mismatch | system_paradox",
    "systemGoal": "真正要理解或改善的系统状态，不是指标",
    "modelGap": "用户当前缺少的对象、关系、条件或边界模型"
  }
}
```

`POST /jobs/course-generation` 没有 contract 或缺少 `problemFraming` 时必须拒绝生成。固定 fallback question 不能合成课程契约。

## 三、叙事生成规则

### 3.1 Plan 阶段输出

Agent 在 Plan 阶段必须产出：

- **drivingQuestion**：一个真实的、值得回答的问题
  - 不是定义式（"X 是什么"）
  - 必须指向认知冲突、设计权衡或机制选择
  - 好："为什么 Git 选择快照而不是增量？"
  - 差："Git 的对象模型是什么？"

- **centralTension**：为什么这个问题难/重要
  - 不是装饰性陈述（"这是一个深刻的问题"）
  - 必须说明认知障碍的根源（"直觉告诉我们 X，但实际是 Y"）

- **overview.arc**：4–6 个章节标题，体现论证弧线
  - 不是知识点列表（"第一章：基础概念"）
  - 必须是论证步骤（"为什么存快照不存增量"）

### 3.2 Chapter 生成输入

Agent 在生成每个 Chapter 时接收：

- **prev_chapter_ending**：上一章的结尾段落（保持叙事连续性）
- **position_in_arc**：本章在论证弧线中的角色
  - `intro`：引入问题，建立直觉冲突
  - `build`：积累证据，深入机制
  - `pivot`：转折点，关键洞察
  - `conclude`：解决张力，回应 drivingQuestion

### 3.3 Narrative 要求

生成的 Chapter 必须：

- **10-18 个 narrative block**，一条主线
  - 不是教材式的"章节 → 小节 → 要点"结构
  - 段落之间有逻辑依赖（不能打乱顺序）

- **概念随论证出现**，不预先列表
  - 不在开头写"本章将介绍 X、Y、Z"
  - 概念在被需要时自然引入

- **零 bullet points**（除非是代码示例或对比表）
  - 避免"有三个原因：1. … 2. … 3. …"
  - 用因果推进代替枚举

- **开头直接进入问题**，不做场景摆拍
  - 禁止"想象你是一个开发者…"式开场
  - 禁止"晚上七点，你盯着屏幕…"式场景描述

## 四、Register（语域）

根据课程的 `knowledgeType` 自动选择叙事语域：

### 3.1 Explainer（解说腔）

**适用**：`procedural`、`factual`、`situational`

**风格**：技术博主（3Blue1Brown、Fireship）

**特征**：
- 用"你"而非"我们"
- 直接动词（"看这个例子""运行这段代码"）
- 可视化类比（"想象一个队列…"）
- 代码 trace 为主
- 清晰的操作步骤

**禁止**：
- 深刻金句（"这就是编程的艺术"）
- 哲学家背书（"正如 Dijkstra 所说…"）
- 为比喻而比喻（"这就像人生一样…"）

### 3.2 Essay（随笔腔）

**适用**：`conceptual`、`strategic`

**风格**：思想随笔（script_background 风格）

**特征**：
- 允许"我"的立场声音
- 哲学追问（"为什么需要…""这意味着什么"）
- 抽象概念对比
- 少代码，多推理
- 论证的张力和转折

**禁止**：
- 技术细节堆砌（"有 17 个参数…"）
- 代码示例充数（用代码替代论证）
- API 文档搬运

### 3.3 Writing Mode（写作/评审模式）

`register` 是大语域，`writingMode` 是生成 prompt 和 judge prompt 共用的内部评审尺子。不要把 `register: essay` 理解成“必须写人物、情节、场景的记叙文”。

默认规则：
- `conceptual`、`strategic`、`metacognitive` → `conceptual-essay`
- `factual`、`procedural`、未知类型 → `mechanism-explainer`
- `case-narrative` 只在 plan 阶段明确选择具体情境/案例轨迹时使用，无效值回退到默认规则

**conceptual-essay** 要完成概念论证：章节 role、概念关系链、事实/文本/经验锚点、受控比较对象。judge 不得因为缺少人物、情节、场景或个人经历而判不合格。

## 五、防八股（四道闸）

### 4.1 事实脊柱

**Plan 阶段要求**：
- 列出 3–5 个可验证事实/案例
- 不是概念定义，是具体案例
- 好："Linux 内核的 O(1) 调度器在 2.6.23 被 CFS 替代"
- 差："调度器有多种实现方式"

**Chapter 生成约束**：
- 每 10 段必须锚定至少 1 个具体事实
- 不允许连续 5 段空转概念（"我们可以认为…""从某种意义上…"）

### 4.2 Register 护栏

**Explainer 禁止**：
- "深刻金句"（"这就是计算机科学的魅力"）
- "哲学家背书"（"正如图灵所言…"）
- "为比喻而比喻"（"这就像生活中…"）
- 抒情段落（"当你真正理解它时，会感到…"）

**Essay 禁止**：
- 技术细节堆砌（把 API 文档复制进来）
- 代码示例充数（用代码块占字数）
- 失去论证主线（变成知识点罗列）

### 4.3 Negative 样本

Prompt 必须注入反例：

```
❌ 不要写成：
"你有没有想过，为什么 X 是这样设计的？其实，这背后有着深刻的道理。让我们从一个故事开始…"

❌ 不要写成：
"想象你是一个开发者，某个深夜，你盯着屏幕，突然意识到…"

✓ 直接进入：
"Git 的快照模型违反直觉。大多数版本控制系统存储文件差异（delta），Git 存储完整快照（snapshot）。这看起来很浪费空间——为什么？"
```

### 4.4 LLM 评审闸

生成后用 judge LLM 评估：

**实质密度（substance density）**：
- 计算"具体事实 vs 空洞陈述"比例
- 低于 30% → 重写

**疑似杜撰（hallucination detection）**：
- 检测不可验证的"研究表明""专家认为"
- 发现疑似杜撰 → 标记段落，要求补充来源或删除

**不通过**：
- 最多重写 2 次
- 仍不通过 → 标记为需人工介入

## 六、知识类型与认知层级

### 5.1 知识类型声明
- 每门课必须标注 `knowledgeType`（单一类型）
- 类型决定 Register 选择（见第三节）

### 5.2 认知层级目标
- 课程整体的 `bloomLevel` 反映目标深度
- `conceptual` 课程通常定位在 `understand` 或 `analyze`
- `procedural` 课程通常定位在 `apply`
- 不强制每章都爬升认知层级（叙事需要可以平稳推进）

---

## 七、质量控制策略

> **架构决策（2026-06-21）**：内容质量由 prompt 层 + LLM 评审层双重控制。

当前策略：
- **prompt 层**：注入叙事理论（register、substance density、continuity）和负面样本
- **LLM 评审层**：生成后用 judge LLM 评估实质密度和杜撰检测（见第四节）
- **normalize 层**：结构完整性检查（必需字段存在性），缺失字段给 fallback 而非 raise
- **engine 层**：仅 title 缺失和 narrative 为空是 error，其余降级为 warning

## 八、生成负面样本

Agent prompt 应包含负面样本（告诉 Agent "不要这样做"）：

### 差的 drivingQuestion
```
✗ "什么是 Transformer？" — 定义式，不触发冲突
✗ "深入理解注意力机制" — 不是问题
✓ "为什么 Attention 不用 CNN 的局部窗口，而要看全部位置？" — 指向设计决策
```

### 差的开场
```
✗ "你有没有想过，为什么 X 是这样设计的？其实，这背后有着深刻的道理…" — 装腔作势
✗ "想象你是一个开发者，某个深夜，你盯着屏幕…" — 场景摆拍
✓ "Git 的快照模型违反直觉。大多数版本控制系统存储文件差异…" — 直接进入问题
```

### 差的叙事模式
```
✗ "有三个原因：1. … 2. … 3. …" — bullet point 枚举
✗ "本章将介绍 X、Y、Z" — 教材式预告
✓ 直接展开论证，概念在需要时自然出现
```

## 九、Human Review Gate

所有 Agent 生成的内容必须经过人工审核。审核不是检查格式（那是质量检查的事），而是判断：

1. **drivingQuestion 是否真的尖锐？** 还是只是符合格式的平庸问题？
2. **叙事是否连贯？** 还是章节之间各自为政？
3. **事实脊柱是否扎实？** 还是空转概念？
4. **Register 是否恰当？** Explainer 有没有装深刻，Essay 有没有堆细节？
5. **课程有没有退化成八股文？** 开场套路、金句堆砌、比喻过度？

审核结果记录在 `review/approval.json`：
```json
{
  "approved": true,
  "reviewedBy": "reviewer-name",
  "reviewedAt": "ISO-8601",
  "notes": "审核意见"
}
```
